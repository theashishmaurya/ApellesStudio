# perf-300 run, 2026-11-10 — after B-379, on a `tauri build --debug` bundle

Measured the way B-347 F6 requires: a `tauri build --debug` app (Rust debug so the
`debug_*` ops exist, with the PRODUCTION web bundle — no React dev tracks, no
StrictMode double render), machine idle at the owner's confirmation, dev server
stopped so nothing competed for CPU or input.

**Build note.** The bundle is `npm run tauri --workspace app -- build --debug`, NOT
`npm run tauri:build -- --debug`. The latter hard-codes
`--config src-tauri/tauri.macos.release.conf.json`, which declares
`binaries/apelles-mcp` and therefore trips D-390's guard ("bundled from a release
build only"). That guard is correct: a release overlay built in debug is the
incoherent thing it exists to catch. The harness wants the plain debug bundle.

## Two measurement caveats, stated rather than papered over

1. **The ctrl-wheel zoom verdict rests on 4 sampled frames.** A p95 over 4 samples
   is not a p95 in any useful sense. The miss is probably real (2026-11-04 recorded
   113 ms p95 on the same step, so 58 ms is an improvement but still high), but it
   needs a step that renders enough frames to measure before anyone acts on the
   number.
2. **The report's "5 dropped of 4 frames (125% > 10%)" is not a percentage.**
   `budgets.ts` computes `dropped / samples`, and those are different populations —
   dropped vblanks against frames actually sampled — so the ratio can legitimately
   exceed 1 while reading as nonsense. Worth either renaming the line or dividing by
   the right denominator; as printed it invites a reader to dismiss a real miss.

# Export benchmark, same day — B-380's closing measurement

`measure_export_benchmark` (`#[ignore]`d), the 60 s explainer-shaped fixture, on an
idle machine with **the app closed**. Default path (the one GPU engine, D-449; in
process VideoToolbox decode and encode, D-452).

| size | wall | ratio | cpu | gpu avg / peak | rss | segs | remux |
|---|---|---|---|---|---|---|---|
| 1920x1080 | 8.1 s | **x0.13** | 5% of 10 | 64% / 83% | +126 MB | 2 | 0.4 s |
| 3840x2160 | 29.5 s | **x0.49** | 4% of 10 | 60% / 88% | +141 MB | 2 | 1.2 s |

Decode floor (one track, 60 s A-roll, VideoToolbox → IOSurface, in process):
1.6 s (x0.03) at 1080p, 5.7 s (x0.10) at 4K.

**B-380's condition — "4K under 1x on the default path" — is met with margin**:
0.49x is about half real time, and matches D-452's own recorded figure exactly.
What is left is the encoder, not the compositor: at 4K the writer sits in the
encoder for 54.9 s of wall time across its workers (`wait-on-writer 52.4 s`)
while the GPU work itself is 3.2 s of frame time and 0.6 s of GPU wait.

## A confound worth recording, because it cost a run and nearly a false bug report

The first attempt **failed**, with:

> the remux stopped responding: it did not exit within 120s of being told its
> input had ended, and was killed. Any output file it was writing is incomplete
> and was never finalised.

That was not a product defect. **The Apelles app was still running**, and D-452
records that every export segment shares the ONE hardware encoder — the reason its
segment ceiling went 6 → 2. A live app plus a benchmark both wanting VideoToolbox
is contention the product never asks a user for. With the app closed, the same
benchmark passes at x0.13 / x0.49.

Two rules for whoever runs this next: **quit the app first**, and note the harness
resolved `/opt/homebrew/bin/ffmpeg` rather than the bundled 9.0.2, so a remux
problem seen here may not be the binary the product ships.
