## B-058 — The Motion tab said "No project open" for the whole session, with a project genuinely open — it inferred that from one read it made at boot, before any project existed
status: fixed (2026-09-05, D-150) · severity: high (the Motion tab was unusable for the entire session with no recovery path an owner would find; Edit and Colorist worked against the same project throughout) · area: `packages/motion/src/{useMotionManifest.ts,MotionTab.tsx}`, `app/src/main.tsx`
- **found:** 2026-09-05, owner-reported live with a screenshot — "Projects ▸ &lt;name&gt;" breadcrumb showing, Edit and Colorist both working against that project, Motion showing "No project open — Open a project in the Colorist tab to edit and render a motion manifest" with a Retry button.
- **repro:** launch the app, open any real `.chroma` project from the launcher, switch to the Motion tab. Nothing about the project matters.
- **expected:** the Motion tab loads that project's manifest (or the engine's sample manifest, for a project that has never saved one).
- **actual:** the "No project open" empty state, for the rest of the session.
- **cause:** two halves, and the second is the one that matters.
  1. **The read happened before there was anything to read.** `Shell.tsx` mounts every tab from boot and merely hides the inactive ones (`{tabs.map(…)}`, L308–315 — deliberate; B-007's note in `app/src/main.tsx` says so), so `MotionTab` → `useMotionManifest` ran its `load()` under the launcher with no project open. `chroma_motion_get_manifest` correctly rejected: `motion.rs::current_project_dir` (L35–39) returns `"no project open — open one in the Colorist tab"` when `state::current_project()` is `None`.
  2. **That failure was then recorded as a fact about the app.** `useMotionManifest`'s `catch` matched that exact string (via `manifestIO`'s `NoProjectOpenError`) and set `loadState = 'no-project'` — an answer with no input that could ever change it. Nothing pushed the app's real "a project is open" signal into this tab (`@chroma/editor` gets exactly that, `setProjectOpen` from the composition root — B-034/D-112), and the one thing that re-read was a window `focus` listener. **Opening a project from the in-window launcher blurs nothing**, so that listener never fired for the real case; only alt-tabbing out of the app and back happened to clear it, which is why the bug could read as intermittent.
- **not a D-148 regression**, though the timing suggested one: `state::set_project(Some(ProjectRef{…}))` still runs at `project.rs` L199, at the end of `open_manifest`, on every open/new/relink/add-shot/remove-clip path, and D-148's diff touches `set_project` only inside test code. It is provable from the screenshot alone, too — the frontend sets `projectPath` (hence the breadcrumb and the tab bar) only from the `ProjectOpenDto` that `open_manifest` returns *after* that line, so a visible tab bar means `set_project` had already run. This bug has been present since the tab shipped (D-046).
- **fix (D-150):** the readiness state moves out of the hook into `packages/motion/src/motionProjectStore.ts`, and the app pushes the signal in (`main.tsx` → `useMotionProjectStore.setProjectOpen`), mirroring B-034/D-112's shape. `load()` refuses to call the backend at all while the signal is false, so there is no error to misread; a read that fails while a project *is* open is `status: 'error'` with the real backend text; "No project open" now has exactly one cause. The signal is deliberately `!!projectPath`, narrower than the shell's own `projectOpen`: an in-memory "Untitled" loose-clip session has no project directory and therefore nowhere to keep a manifest sidecar, so the empty state (reworded to say so) is the truth there rather than a lie.
- **regression tests:** `packages/motion/src/motionProjectStore.test.ts`, 9 tests. Two encode this exact fault and were **confirmed to fail against the pre-fix behaviour** (the old inference + unguarded mount read temporarily restored inside the new store): `never runs at all while the app says no project is open` and `even the backend's own "no project open" text does not flip the signal`.
- **verification gap (honest):** proven by test and by tracing, not by driving the real Tauri window — this pass ran in a sandboxed worktree that cannot launch the app (and must not touch the owner's live dev server). Same constraint D-125/D-130 recorded for their timing fixes.
- **adjacent hole found, deliberately NOT fixed here:** `useSessionStore.closeProject` leaves the Rust `state::ProjectRef` pointing at the closed project (its own comment calls this harmless). That is not harmless for a loose-clip "Untitled" session opened afterwards — every `current_project_dir()` consumer (`edit.rs`, `motion.rs`, `export.rs`) would resolve into the *previous* project's directory. Motion no longer reaches that path (its signal is false for an Untitled session); the Edit tab's exposure is pre-existing and out of this pass's scope. Filed here so it is not re-derived from scratch later.
## B-059 — A camera keyframe's `ease` is supported by the engine and silently stripped by the schema, so every camera move in every manifest is stuck on the default easing
status: fixed (2026-09-05, D-159) · severity: low (a real engine capability is unreachable from a manifest; the fallback is the sensible `design.ease.inOut`, so nothing looks broken — it just cannot be changed) · area: `packages/motion-engine/src/engine/schema.ts` L32–37 (`cam2dKey`)
- **found:** 2026-09-05, writing `docs/notes/motion-tab-audit.md` (D-151) — while fact-checking that audit's own draft claim that Motion's camera interpolation was "linear, no easing control." That claim was **wrong**, and checking it turned up this instead.
- **repro:** put an `ease` on a 2D camera key in a manifest — `{"at": 1.6, "zoom": 1.5, "ease": [0.4, 0, 0.2, 1]}` — and parse it through `manifestSchema`. Verified live via a scratch script: the parsed key comes back `{"at":0,"zoom":1}`, i.e. `'ease' in key === false`.
- **expected:** the `ease` reaches `Camera`, which has genuinely supported it since the primitive was written — `CameraKey.ease?: readonly [number,number,number,number]` (`Camera.tsx` L20–26), applied as `Easing.bezier(...)` at L30 and consumed at L73. `Video.tsx` L29 already spreads the key through verbatim (`{ ...k, at: … }`), so the plumbing between schema and primitive is complete and correct on both sides — the schema is the only thing in the way.
- **actual:** `cam2dKey` is a plain `z.object({at, x?, y?, zoom?})`, and zod strips unknown keys by default, so `ease` is removed during validation before `Video.tsx` ever sees it. Every camera move in every manifest therefore runs on `design.ease.inOut` (`Camera.tsx` L46's `k.ease ?? design.ease.inOut`), with no way to say otherwise.
- **cause:** the sibling `layer` schema *is* `.passthrough()` (`schema.ts` L64) precisely so per-primitive props survive without being re-declared centrally — the author knew about the distinction and applied it one object over, but not to the camera keys. `cam3dKey` (L39–43) has the same strict shape — this bug's own original text guessed that was "harmless... since Scene3D has no ease concept," which **D-159 found to be wrong**: `Scene3D.tsx`'s `CameraRig` reads `CamKey.ease` the identical way (`cb(b.ease ?? design.ease.inOut)`), so `cam3dKey` had the exact same live bug, just never separately filed.
- **fix (D-159, applied exactly as proposed below):** `cam2dKey` (and, per the finding above, `cam3dKey` too) now declares `ease` as a real, typed `easeCurve` (`z.tuple([z.number(),z.number(),z.number(),z.number()])`) field rather than reaching for `.passthrough()` — visible to `propCatalog.ts`'s `CAM2D_KEY_FIELDS`/`CAM3D_KEY_FIELDS`, which now expose it as a real `[x1,y1,x2,y2]` JSON-tuple control in the Inspector's existing camera keyframe editor, completing this bug's own proposed fix text verbatim. The same `easeCurve` shape is also used by the new `transformKey` (D-159's per-layer keyframes), so a THIRD potential instance of this exact gap never gets a chance to exist.
- **verification:** `packages/motion/src/schema.test.ts` (5 tests) — an authored `ease` round-trips through `manifestSchema.parse` on a 2D camera key, a 3D camera key, and a new layer transform key; a key with no `ease` still parses correctly (no regression); and one test reconstructs the EXACT pre-fix `cam2dKey` shape inline, proves it strips `ease` (this bug's own repro, reproduced), then proves the current schema does not — a test that would have failed against the old schema, not merely one that passes against the new one. See D-159's own decision entry (`docs/08-decisions.md`) for the full write-up.

## B-061 — the Motion Inspector labels camera keyframe times in frames; the manifest stores seconds
status: open · severity: low (a mistyped value, not a crash — but a silently wrong one) · area: `packages/motion/src/propCatalog.ts` (`CAM2D_KEY_FIELDS`, `CAM3D_KEY_FIELDS`)
- **found:** 2026-09-05, reading the Motion tab for the D-152 visual-builder research pass. Not owner-reported.
- **repro:** Motion tab → select a scene's `Camera` row → the keyframe list editor (`InspectorPanel.tsx` L327–341) renders `CAM2D_KEY_FIELDS`, whose first field is labelled **"At (frame)"**. Type `48`, intending frame 48 of a 30 fps composition.
- **expected:** the key lands 1.6 s in. Every other timing field in the same Inspector is labelled "(s)" (`timingFields`' "Start (s)" / "Duration (s)", `SCENE_FIELDS`' "Duration (s)"), and the manifest is uniformly seconds.
- **actual:** the key lands at 48 **seconds** — past the end of most scenes, so the camera move silently never happens.
- **cause:** `propCatalog.ts` labels both `CAM2D_KEY_FIELDS[0]` and `CAM3D_KEY_FIELDS[0]` as `'At (frame)'`. The manifest's unit is seconds — `schema.ts`'s header says "All times are in SECONDS" and its own example uses `{"at":0.3,…}`; `Video.tsx` converts on the way in with `Math.round(k.at * fps)`. The stored value and the engine agree; only the label is wrong.
- **fix:** relabel both to `'At (s)'`. One word, one file, no data or schema implication. Worth doing alongside a step/precision pass on the field — a `1` step on a seconds value is a whole-second jump per keystroke, the same class of defect D-136 fixed on `ClipInspectorPanel`'s Position X/Y after the normalisation migration.

## B-060 — the ambient drift's rate is computed from a hardcoded 30 fps token, so the same manifest is not the same motion at two frame rates
status: open · severity: low (±3 px, deterministic, invisible at the default fps — a consistency defect, not a visible break) · area: `packages/motion-engine/src/primitives/Camera.tsx`, `packages/motion-engine/src/lib/draw.ts` (`ambientDrift`)
- **found:** 2026-09-05, reading `Camera.tsx` in full for the D-152 research pass — the camera transform had to be written out exactly to answer the coordinate-space question, and the drift term does not survive that. Not owner-reported.
- **repro:** render any manifest twice, identical but for `"fps": 30` vs `"fps": 60`. Compare the same wall-clock instant in each.
- **expected:** frame rate is a render-quality/timing knob; the *motion* — where things are at a given second — is the same. Every other time-driven value in the engine already honours this: `registry.ts`'s `f(sec, fps)` converts through the real fps, `Video.tsx` sizes each `<Series.Sequence>` from it, and every primitive reads `useVideoConfig().fps`.
- **actual:** the drift oscillates twice as fast in wall-clock at 60 fps, and 20 % slower at 24 fps.
- **cause:** both drift implementations divide the frame number by **`design.fps`** — a design *token* fixed at `30` (`design.ts` L32) — rather than by the composition's own fps. `Camera.tsx` L81–85: `design.ambientDriftPx * 2 * Math.sin((frame / design.fps) * 0.6)`. `draw.ts`'s `ambientDrift` (L36–39) repeats the same expression. `Camera` already calls `useVideoConfig()` for `width`/`height`, so the correct value is in scope and unused; `draw.ts` is a pure helper and would take `fps` as a parameter, the way `pop(frame, fps, delay)` in the same file already does.
- **fix:** use the composition's fps in both. `design.fps` stays as the *authoring default* (what a new manifest gets) and stops being read as a runtime constant. One consequence to accept before doing it: this changes rendered pixels for any non-30 fps manifest — correct, but a real look change, so it wants its own commit and a before/after frame rather than riding along with something else.

## B-062 — a key's `ease` had no validation anywhere against `Easing.bezier`'s own hard `x∈[0,1]` requirement, so an out-of-range hand-authored value renders fine right up until it crashes
status: open · severity: low (requires hand-editing the manifest text or a foreign tool to produce; the Inspector's own new curve widget, D-164, cannot produce this value by construction) · area: `packages/motion-engine/src/engine/schema.ts` (`easeCurve`), `node_modules/remotion/dist/cjs/bezier.js`
- **found:** 2026-09-05, building the Phase 5b curve/easing editor (D-164) — confirming `Easing.bezier`'s real signature against `remotion`'s own bundled source (not assumed) surfaced its own hard guard: `bezier(mX1,mY1,mX2,mY2)` THROWS `'bezier x values must be in [0, 1] range'` unless `0 <= mX1,mX2 <= 1`. `y1`/`y2` carry no such constraint at all (`design.ease.anticipate` already overshoots to `y1:-0.55`/`y2:1.55`).
- **repro:** hand-edit a manifest's `ease` to `[-1, 0, 2, 1]` (via the Inspector's manifest-text `</>` toggle, or any other tool/script that writes the JSON directly) and render/preview any key that reaches it.
- **expected:** either the schema rejects an `x1`/`x2` outside `[0,1]` at parse time (a clear, early error), or the engine clamps defensively before calling `Easing.bezier`.
- **actual:** `schema.ts`'s `easeCurve` is `z.tuple([z.number(),z.number(),z.number(),z.number()])` — any four finite numbers pass. Nothing between the schema and `interpolateKeys.ts`'s `Easing.bezier(c[0],c[1],c[2],c[3])` call checks the `x` range, so the manifest validates and the render throws only when playback/rendering actually reaches that key's own frame — a late, confusing failure mode (looks like an engine crash, not a data problem).
- **cause:** the schema was written (D-159/B-059) to fix a *different* gap — `ease` being silently STRIPPED — and correctly declared the field's SHAPE (a 4-tuple of numbers), but never encoded the one real semantic constraint the consuming function (`remotion`'s own `bezier()`) enforces at its own call boundary. A `z.tuple` has no built-in way to say "elements 0 and 2 specifically must be in `[0,1]`"; that needs a `.refine()` or a narrower per-position schema, neither of which existed at either B-059 or this pass.
- **not fixed here, deliberately:** this pass (D-164, the curve/easing editor) was explicitly scoped to a NEW INPUT WIDGET for an already-plumbed field, not a schema change — a real widget-side mitigation exists instead (`easeCurve.ts`'s `pixelToCurve` unconditionally clamps a drag's `x` to `[0,1]`, so the new Inspector control can never itself author an invalid value) — but that only protects the ONE authoring path this pass touched. The manifest-text editor (`ManifestEditor.tsx`'s raw JSON view) and any external tool/script remain unguarded. A real fix is a `schema.ts` change (a `.refine()` on `easeCurve`, or splitting it into a stricter tuple type) — flagged here rather than smuggled into a pass whose own task brief explicitly said "if you find yourself needing a manifest/schema change, stop and reconsider."
- **fix (proposed, not applied):** `easeCurve = z.tuple([z.number(), z.number(), z.number(), z.number()]).refine(([x1, , x2]) => x1 >= 0 && x1 <= 1 && x2 >= 0 && x2 <= 1, 'ease x1/x2 must be within [0,1]')` — a real parse-time rejection instead of a render-time crash, at the one place (`schema.ts`) already responsible for this field's shape.

## B-056 — `edit::PROBE_CACHE` never invalidates and is keyed on path alone, so a source file replaced in place serves stale `VideoInfo` for the rest of the session — defeating the staleness guarantee the disk cache directly beneath it was built to provide
status: fixed (2026-09-05, D-146) · severity: medium (wrong duration / frame count / resolution / fps everywhere downstream; recovery is an app restart, with no indication that is what is needed) · area: was `app/src-tauri/src/chroma/edit.rs` L93–128 (`PROBE_CACHE`, `probe_cached`); now `crates/chroma-media/src/probe.rs`
- **found:** 2026-09-05, reading `probe_cached` for the D-141 crate-extraction scoping pass (`docs/notes/crate-extraction-plan.md` §2.2) — `probe_cached` has to move out of `edit.rs` before `chroma-media` can exist, and it does not survive being looked at closely. Not owner-reported.
- **repro:** open a project with a clip. Scrub it, so `probe_cached(path)` populates. Without quitting the app, replace that file at the same path with a different encode of it — a re-export from another tool over the same filename, a re-render, an `ffmpeg -i … -c:v … same.mov`. Anything that changes duration, resolution or frame rate is enough. Now interact with the clip again.
- **expected:** the app re-probes and picks the new file's real facts up — which is precisely what the disk layer one line below is designed to do. `media_cache::source_key` is `blake3(path ‖ mtime_nanos ‖ len)` specifically so that "a re-encoded or replaced file never serves a stale probe" (`edit.rs` L106–108; `media_cache.rs` L89–104 argues the choice at length).
- **actual:** the in-memory layer *in front of it* returns the old `VideoInfo` and the disk layer is never consulted. Every consumer gets stale facts for the process lifetime: `edit::composition_size` (so D-136's whole composition-space model, and therefore every layer's normalised position and scale), `edit::build_from_shots` (clip lengths in frames), `filmstrip::chroma_clip_thumbnails` (strip extent — and the stale `info` is handed to `extract_thumb_chunk`, while `media_cache`'s own chunk key correctly misses, so it re-decodes with wrong metadata), `audio::cached_peaks`, `project`'s `MediaItem`/`MediaVideoInfo` DTOs, and `decode_pipe`'s `-ss (start-0.5)/fps` seek arithmetic.
- **cause:** `static PROBE_CACHE: Lazy<Mutex<HashMap<PathBuf, VideoInfo>>>` is **insert-only**. `grep -rn PROBE_CACHE` finds four sites: the declaration and three inside `probe_cached` (one read, two inserts). There is no `clear`, no eviction, no TTL, and — the actual defect — no re-validation of the key against the file's current mtime/size, even though the very next lines compute exactly that value for the disk lookup. The two-layer cache therefore has two different keys for the same question, and the weaker one is in front. `chroma_project_relink` looks like it should paper over this and does not: it calls `video::probe` directly for the manifest, and relinking points at a *new* path anyway (a new key), so it never touches the stale entry for the old one.
- **fix (D-146, applied in the `chroma-media` commit-2 move exactly as this entry proposed):** validate on hit. `media_cache::source_key(path)` is now computed **first**, before the memory lookup rather than after it, and `PROBE_CACHE` stores it beside the `VideoInfo` (`HashMap<PathBuf, (String, VideoInfo)>`). A hit whose stored key differs from the file's current one falls through to the disk layer and then to a real `ffprobe`, overwriting the entry; both layers now answer the same staleness question with the same key instead of the weaker one shadowing the stronger. Cost is one `stat` per hit — the same order as the `HashMap` lookup it guards, and orders of magnitude below the `ffprobe` spawn it avoids (measured: an unchanged file is still >5x cheaper warm than cold, asserted by `an_unchanged_file_is_still_served_from_memory`).
- **one deliberate decision the entry did not cover:** when `source_key` fails outright — the file cannot be `stat`ed, i.e. the media went **offline**, which `project::media_item_is_online` treats as a real supported state — the remembered `VideoInfo` is served *unvalidated* rather than becoming an error. Re-probing a file that cannot be opened would fail anyway, and reporting a clip's known duration beats reporting nothing. Pinned by `an_offline_file_still_serves_its_remembered_facts`. Correspondingly, a probe with no `source_key` is **not** memoised at all — an unkeyed entry would be precisely the insert-only cache this bug was about.
- **regression test:** `chroma_media::probe::tests::a_source_file_replaced_in_place_is_re_probed_not_served_stale` — synthesises a real 320x240/1s clip with `ffmpeg`, probes it, overwrites the same path with a real 640x480/2s clip, and asserts the second probe reports 640x480. **Confirmed to fail against the pre-fix code** (the old body temporarily restored in place): `left: 320, right: 640`.

## B-057 — `filmstrip::CHUNK_LOCKS` leaks its entry whenever a chunk extraction fails, because the cleanup sits after the `?`
status: fixed (2026-09-05, D-146) · severity: low (a bounded leak of small entries; no user-visible symptom found) · area: was `app/src-tauri/src/chroma/filmstrip.rs` (`load_chunk`); now `crates/chroma-media/src/filmstrip.rs`
- **found:** 2026-09-05, reading `load_chunk`'s locking for the D-141 crate-extraction scoping pass. Not owner-reported, and filed as low rather than dressed up: it is a real defect with a one-line fix, not a performance problem.
- **repro:** request a filmstrip window for a clip whose extraction fails — a media-offline clip (`project::media_item_is_online` is a real supported state), a codec `ffmpeg` refuses, or the class of failure B-055 documents. Each *distinct* failing `(source, level, index)` adds a permanent entry.
- **expected:** `CHUNK_LOCKS` holds an entry only while a chunk is genuinely being worked on, which is what the `remove` at the end of `load_chunk` exists to enforce.
- **actual:** on the failure path `let bytes = extract(...).await?;` returns early, so `CHUNK_LOCKS.lock().remove(&key)` never runs and the `String` key plus its `Arc<tokio::sync::Mutex<()>>` stay in the map for the process lifetime.
- **cause:** the cleanup is placed after the fallible call rather than tied to the guard's lifetime. Growth is bounded by the number of distinct chunk keys that have ever failed, not unbounded — which is why this is low and not medium — but `CHUNK_LOCKS` is the one map in this module with no bound at all (`CHUNK_MEM` has `MAX_CHUNK_MEM`, `KEYFRAME_MEM` is per-path, the disk cache has `CACHE_BUDGET_BYTES`), so it is the one place the module's own discipline is missing.
- **fix (D-146, applied in the `chroma-media` commit-3 move):** a `ChunkLockGuard { key }` whose `Drop` removes the entry, taken immediately after the `tokio` mutex guard and never released early. Drop order is the reverse of declaration, so the entry is removed **while that lock is still held** — byte-for-byte the ordering the old success path had, which this entry's own "checked and explicitly NOT a bug" note already traced as safe. The trailing `CHUNK_LOCKS.remove(&key)` statement is gone entirely; there is now no path out of `load_chunk` (early `Ok` from either `CHUNK_MEM` re-check, the `?` on a failed `extract`, or the normal return) that leaves an entry behind.
- **regression test:** `chroma_media::filmstrip::tests::a_failed_chunk_extraction_does_not_leak_its_chunk_lock` — writes a real file whose contents `ffmpeg` refuses (so it has a real `source_key` and therefore genuinely takes the lock path), calls `load_chunk`, asserts the call really failed and that `CHUNK_LOCKS` is back to its prior size and no longer holds that chunk's key. **Confirmed to fail against the pre-fix code** (the guard removed and the old trailing `remove` restored in place): `left: 1, right: 0`. Counted as a delta, not an absolute, because `CHUNK_LOCKS` is a process-global and `cargo test` runs the binary's tests in parallel. Paired with `a_successful_chunk_load_also_releases_its_chunk_lock` (env-gated on `CHROMA_TEST_VIDEO`) so the guard cannot regress the path that already worked.
- **checked and explicitly NOT a bug:** the neighbouring question — whether removing the entry *while still holding the lock* lets a second task start a duplicate `extract` — was traced and does not reach. A third caller arriving in that window hits `CHUNK_MEM` (`remember` runs before the `remove`), and even if `remember`'s wholesale `mem.clear()` had just evicted it, `media_cache::write_blob` has already run before `remember`, so that caller takes the disk hit and never re-decodes. Recorded here so it is not re-derived as a suspicion later.

## B-053 — A lone clip's transform was silently discarded by the preview: the single-layer fast path skipped compositing unconditionally
status: fixed (2026-09-04, D-132) · severity: high (an Inspector control that writes the file and changes nothing on screen) · area: `app/src-tauri/src/chroma/edit.rs` (`timeline_frame`)
- **found:** 2026-09-04, while wiring D-132's per-clip crop through the Edit-tab compositor. Not reported by the owner — found by asking "what happens when there's only one clip," which is the first thing anyone would try a crop on.
- **repro:** one video clip on one track, nothing above or below it. Select it, set Opacity `0.5` (or Scale `2`, or Rotation `45`) in the Edit-tab Inspector.
- **expected:** the preview shows the change, the way it does the moment a second visible video track exists.
- **actual:** nothing changes on screen, at any playhead position or preview quality. The value really is written to `project.json` and really is read back into the Inspector field — only the picture never reflects it.
- **cause:** `timeline_frame`'s `match layers.as_slice()` had `[(track, clip, source_frame)]` as an **unconditional** arm — "exactly one visible layer needs no compositing at all" (D-088). True for a *plain* clip, and a real, worthwhile fast path (it skips a full-frame RGBA clone, an alpha pass and an `overlay`); false for a clip carrying any of the D-082 transform fields, which only `composite_layer_onto` ever applies. So the transform was reachable in the UI, persisted, keyframeable — and invisible, for the entire single-track case, which is most projects.
- **fix (D-132):** the arm is now guarded by `resolve_clip_transform(clip, *source_frame).is_identity()`. A genuinely untransformed clip still takes the plain-decode path byte-for-byte (the common case costs exactly what it did before); anything else falls through to the real compositor. `is_identity()` deliberately shares `crop_pixel_rect`'s clamp semantics so the predicate can never disagree with what would actually be painted.
- **remaining caveat at the time this was written, since closed:** this makes a lone clip's `position_x`/`position_y` visible for the first time — and at the time, those were still **B-043**-affected (absolute pixels in a canvas whose size follows the preview decode scale), so a lone clip's *position* would still shift between scrubbing and playing until Phase 0a of `docs/notes/on-canvas-transform.md` landed. Nothing had forced this into the open earlier because there is still **no timeline export path** — `chroma::export::export_video` is Colorist's single-clip path — so no code had ever had to answer "what resolution is the composition."
- **fix (D-136):** the timeline gets a real composition space — `ProjectSettings.width`/`height` (D-038), or the timeline's first video clip's probed resolution as fallback. `composite_video_frame`'s canvas is now that composition (downscaled uniformly to `max_long_edge` for the preview), each layer's footprint is its own SOURCE resolution mapped through the composition (not its decoded buffer's size), and `Clip::position_x`/`position_y` are normalised fractions of that composition — correct at every preview scale by construction, the same reasoning D-132's crop insets already used. A new `chroma_timeline_clip_geometry` Tauri command reports a clip's natural composition-space footprint for a frontend overlay to use. **Existing pixel-valued positions are migrated**, not silently reinterpreted in place: `chroma.project`'s schema gained a minor (`1.1`, `NORMALISED_GEOMETRY_MINOR`), a pre-`1.1` file's positions are reinterpreted as composition pixels and divided down on load (`Timeline::normalise_legacy_positions`, D-136 in `docs/08-decisions.md` has the full reasoning for why this can only be a stated reinterpretation, and why every project that never used a PIP offset — i.e. every project until someone drags one — migrates to bit-identical zeros), and the file is restamped so the same values are never divided twice.
- **verification:** `cargo test -p chroma-timeline` 115/115 (4 new migration tests); `cargo test -p RapidRAW --lib -- chroma::edit::` 23/23, including `geometry_is_identical_at_every_render_scale` — the actual regression test, the same decoded layer buffer composited into a 100×100 and a 300×300 canvas, asserting the painted fraction agrees within 1% at both. Full verification and the Phase 1 on-canvas-handles work landed alongside this: D-136.

## B-042 — Crop (and straighten / flip / lens correction) is silently discarded on a Colorist video export: the preview shows one frame, the encoded file contains another

## B-044 — The waveform had no cache at all, and re-decoded a clip's entire audio on every zoom step, on the main thread
status: fixed (2026-09-04, D-129) · severity: high (the same defect D-124 fixed for the filmstrip, still live in the sibling path, and blocking the UI thread while it ran) · area: `app/src-tauri/src/chroma/audio.rs`, `packages/editor/src/Waveform.tsx`
- **repro:** open a project with a long clip that has audio; zoom, or drag a panel divider to resize the timeline.

status: fixed (2026-09-04, D-117) · severity: medium (a real, discoverable feature the owner expected to work, silently no-op'd instead of erroring — easy to mistake for "this feature doesn't exist" rather than "this drop landed nowhere") · area: `packages/editor/src/TimelinePane.tsx`
- **found:** owner, live, single-track project: "i cant drag a clip to create a new track."
- **cause, confirmed via code trace:** this feature (auto-create a track at a drop's insertion boundary) has existed since D-095/D-096, but only for the legacy native-HTML5 Sources-panel-add path (`onDragOver`/`onDrop`, `trackInsertBoundary`). D-100's rewrite moved *clip move* (repositioning an already-placed clip, same-track or cross-track) onto a separate `@dnd-kit/core` drag system (`ClipBody`/`onDndDragMove`/`onDndDragEnd`) — and `TrackDropZone`, the droppable each track row registers, only ever mounts one instance per EXISTING track (`tracks.map`). There was never a droppable for "past the last row" in the dnd-kit path at all, so `onDndDragEnd`'s `if (!overData || overData.type !== 'track') return;` silently cancelled the drag with zero feedback whenever the owner tried exactly this gesture.
- **fix:** rather than mount more droppables (two boundary concepts to keep in sync), `onDndDragMove`/`onDndDragEnd` now compute the same boundary `trackInsertBoundary` already defines for the legacy path — from the dragged `ClipBody`'s own live rect (`event.active.rect.current.translated`, dnd-kit's real signal for "where is this being dragged right now," since dnd-kit doesn't hand back a raw pointer position) instead of a native `clientY`. When a real boundary is found, `onDndDragEnd` runs the identical `add_track` (+ `move_track` when it's not a plain append, + the same selection-follow math the track-reorder drag already uses) the Sources-panel `onDrop` runs, then applies the clip's own `move` onto the freshly-created (guaranteed-empty) track. The live ghost-row preview (`insertPreview`'s `'new_track'` case, already built for the Sources-panel path) now shows during a clip drag too, not just a media drag.
- **verification:** `tsc --noEmit` clean, 136/136 `packages/editor` tests pass (unchanged — the reused `trackInsertBoundary`/op-sequence logic already has coverage via the Sources-panel path; the new dnd-kit wiring itself has no dedicated test, see the honest gap below). **Real interactive (browser/DOM) verification was not performed this pass** — `packages/editor`'s vitest config runs in a `node` environment with no `@testing-library`/jsdom, and dnd-kit's pointer-sensor-driven interaction genuinely needs a real DOM to exercise; building that harness from scratch was judged out of scope for a focused fix. This is the same class of "correct by careful tracing, not yet interactively confirmed" gap other fixes tonight have flagged — the owner's own retest is what closes the loop. Full writeup: D-117 in `docs/08-decisions.md`.

## B-037 — Filmstrip thumbnail generation spawned unbounded concurrent `ffmpeg` processes; software HEVC decode alone was expensive enough to starve the machine
status: fixed (2026-09-04, D-121) · severity: high (a real live incident, not theoretical — the owner's actual machine became barely usable) · area: `app/src-tauri/src/chroma/{edit.rs,video.rs}`, `packages/editor/src/Filmstrip.tsx`
- **found:** owner, live: 11 simultaneous `ffmpeg` processes observed via `ps aux`, system load past 200, immediately after D-119's filmstrip feature shipped and a multi-clip project was opened. A related report minutes later ("the playback and loading player visual when we move the clip is very slow") turned out to be the same root cause, not a second bug — the machine was still recovering from the burst.
- **cause, two compounding, both confirmed not guessed:** (1) `chroma_clip_thumbnails` had no concurrency limit at all — every visible clip's `Filmstrip.tsx` requests its strip independently on mount, each spawning its own `ffmpeg` via `tokio::task::spawn_blocking` with nothing throttling how many run at once. The frontend's silent catch now `console.error`s the real failure before its existing empty-array soft-fail.
- **verification:** both CPU/time numbers measured directly (`time ffmpeg ...` against the owner's real downloaded source file). `cargo test -p chroma-timeline` + `cargo clippy -D warnings` clean; `tsc` clean. **Honest gap**: the concurrency cap itself was not re-proven against a live multi-process burst — no way to launch the full Tauri app with a real window in this environment. Full writeup: D-121 in `docs/08-decisions.md`.

## B-034 — "No project open" on the Edit tab, for the FIFTH time — the pattern across all five is the real bug: a non-atomic `project.json` write torn by the app's own per-frame reader, on top of a UI that reported *any* failed timeline fetch as "no project is open"
status: fixed (2026-09-04, D-112) · severity: high (a false, terminal-looking screen on the app's main entry point; the torn-write half is **not** dev-mode-only — it can corrupt a read in a production build too) · area: `app/src-tauri/src/chroma/project.rs` (`save_manifest`), `packages/editor/src/{timelineStore,EditorTab}.tsx`, `app/src/main.tsx`, `app/src/utils/tauriListeners.ts`

### Read this entry as the closing note on B-004 / B-025 / B-031 / B-032, not as a sixth isolated defect

Five times across two nights the owner opened a project and the Edit tab said **"No project
open"**. Five investigations each found a *genuinely real, genuinely different* root cause,
fixed it correctly, and reported it fixed — and the symptom came back:

| | real cause found | correctly fixed? |
|---|---|---|
| **B-004** | `app/index.html` loaded `/src/main.jsx` instead of `/src/main.tsx`, double-executing the entry module on cold boot and corrupting Tauri's IPC bridge | yes — **re-verified still in place this pass**, `index.html` line 15 is `/src/main.tsx` |
| **B-025** | no loading feedback during a real multi-second open → a second click hit `openProject`'s `busy` guard (D-085) | yes, for the double-click half |
| **B-031** | `open_manifest` resolved the active clip's session index against a non-deduplicated path list, silently aborting the whole open **before `state::set_project` ever ran** (`373e725`) | yes, verified, still correct |
| **B-032** | Vite HMR racing Tauri's async `listen()` teardown, throwing inside `_unlisten` | **no — see below. The fix did not hold.** |
| **B-034** (this) | non-atomic `save_manifest` torn by the per-frame `load_manifest` reader | — |

**The thing nobody logged for four rounds: none of those five faults could produce that
sentence on their own.** Every one of them was some flavour of "a `chroma_timeline_get` call
failed or never came back." It was `EditorTab.tsx` that turned that into a confident claim
that no project was open, because `loaded && !timeline` was the only state it had — no way to
distinguish *"nothing is open"* from *"something is open and its timeline fetch failed."* The
shell directly above it was showing the tab bar at the same moment, which it only ever does
**because a project is open**. The app was contradicting itself on one screen, and every
investigation dutifully went hunting for a new way to break the fetch instead of asking why a
broken fetch was allowed to say that. D-112 fixes the *reporting*, which is what makes this
class of bug diagnosable at all, and fixes the two live faults found underneath it.

### Fault 1 (new, real, production-affecting) — the manifest could be read while it was half-written

- **cause:** `save_manifest` was a plain `std::fs::write`, which truncates `project.json` to
  zero and then streams the new bytes. Meanwhile `load_manifest` runs on a genuinely hot
  path — `chroma::edit::resolve_timeline` re-reads and re-parses `project.json` **from disk on
  every single preview frame** (`chroma_timeline_frame`, i.e. once per frame while scrubbing or
  playing) — while `chroma_timeline_set` rewrites it every 400ms throughout any drag or trim.
  Scrub while an edit is saving and the reader lands inside the write window.
- **what the user sees:** `chroma_timeline_get` returns
  `parse …/project.json: EOF while parsing a value at line 1 column 0`, `load()` fails, and
  (pre-fix) the Edit tab renders that as "No project open".
- **measured, not theorised:** the new regression test
  (`concurrent_saves_never_expose_a_torn_manifest`) run against the *old* `fs::write`
  implementation produced **150 torn reads out of 600 — a 25% failure rate**, every one of them
  that exact `EOF while parsing` error.
- **fix:** write a uniquely-named temp file in the project dir, then `rename` it over
  `project.json`. `rename(2)` is atomic, so a reader now always sees either the complete old
  manifest or the complete new one. Verified against a copy of the owner's own real
  `New.chroma`: **2000 concurrent reads under a continuous writer, 0 torn.**

### Fault 2 (a real recurrence — B-032's fix never actually worked)

- B-032 shipped `safeUnlisten()` wrapping the unlisten call in `try { f?.(); } catch {}`. The
  owner's own dev log, on a freshly restarted instance **built with that fix in it**, shows the
  identical `TypeError: undefined is not an object (evaluating 'listeners[eventId].handlerId')`
  still arriving — as an **unhandled rejection**, with a stack pointing straight at that
  `f?.()` line (`src/utils/tauriListeners.ts:22:12`), at 1:05:26pm on 2026-09-04.
- **why it didn't hold:** Tauri's `listen()` resolves to `async () => _unlisten(event, eventId)`,
  and `_unlisten` is itself `async`. An `async` function never throws synchronously — its first
  statement blowing up produces a *rejected promise*, which a `try`/`catch` around the call
  cannot see. The returned promise was dropped unhandled. A correct-looking guard, guarding the
  wrong half of the failure.
- **fix:** return the call's result into `safeUnlisten`'s own promise chain so the existing
  `.catch` actually catches it.

### What actually triggered occurrence #5 specifically — and it was not a code bug

Reconstructed from `/tmp/chroma-tauri-dev.log` and `project.json`'s mtime, and worth recording
because it wasted a whole investigation:

- `13:02:48` — the owner's open **succeeded**. `open_manifest` wrote `project.json` (that write
  happens immediately before `state::set_project`), so the backend was fully open.
- `13:02:51` — three seconds later, **a different agent working in the same working tree saved
  files**, and Vite HMR pushed `main.tsx`, `EditorTab.tsx`, `TimelinePane.tsx`, `PreviewPane.tsx`,
  `TimelineSwitcher.tsx` and `SourcesPanel.tsx` into the owner's live session.
- `13:02:55` — that intermediate code threw
  (`TypeError: undefined is not an object (evaluating 'dest.clips')` in `timeline.ts`'s
  `resolveClipLanding`, mid-drag), then `hmr invalidate /src/main.tsx` → **`page reload
  src/main.tsx`**, and `You are calling ReactDOMClient.createRoot() on a container that has
  already been passed to createRoot() before` — B-004's exact double-execution symptom, arriving
  by a completely different route.
- `13:03:18` — `[vite] Failed to reload EditorTab.tsx / TimelinePane.tsx / main.tsx …
  TypeError: Importing a module script failed` — the module graph failed to reload at all.
- `13:03:31` — a flood of `[TAURI] Couldn't find callback id …`, i.e. every `invoke` that was

So occurrence #5's trigger was dev-server contamination, not a fifth pipeline bug. That does
**not** make it noise: it is exactly the kind of transient the app must survive, and pre-fix it
was terminal, because a `load()` whose invoke never settles left the tab pinned on a screen

- **process note (please act on this one):** the owner cannot get a trustworthy live test while
  other agents are editing `app/src` or `packages/*` against the same dev server. Either test
  against a quiesced tree, or give live testing its own worktree/dev server. Four of these five
  investigations were conducted against an app being rewritten underneath the tester.

### Fix (D-112) — one signal, one state machine, three real guarantees

- **`projectOpen` is now pushed into the store** from the composition root (`main.tsx` →
  `setProjectOpen`), which reads the app's actual source of truth (`useSessionStore.projectPath`
  — the same value the shell uses to decide to show the tabs at all). Layering is unchanged and
  correct (app → tabs, D-039): `@chroma/editor` is *told*, it never reaches up to ask.
- **`status: 'idle' | 'loading' | 'ready' | 'error'`** replaces `loaded: boolean`. `EditorTab`
  renders "No project open" **only** when `!projectOpen`; a failed fetch with a project open
  renders "Couldn't load the timeline" with the real backend error and a Retry.
- **`load()` is token-guarded.** It is called from five independent places (tab mount, every OS
  window `focus`, the composition-root bridge, the retry ladder, timeline create/switch) and
  nothing ever ordered them — the *slower* call won by writing last, so a stale failure could
  overwrite a fresh success. Only the newest token may write now.
- **`load()` has a timeout** (`LOAD_TIMEOUT_MS`), so the "Couldn't find callback id" case above
  fails honestly instead of hanging forever.
- **Bounded retry ladder** (250/750/2000ms) on `setProjectOpen(true)`, superseding D-085's
  unexplained 500ms one-shot; it gives up into a real error screen rather than looping silently.
- Also fixed here, because it blocked verifying any of the above: **`cargo test` did not compile
  on `main`** — D-107/D-109's `Track::sync_locked` field and D-104's `move_clip(…, ripple)`
  parameter never updated the test initializers in `chroma/project.rs` and `chroma/audio.rs`
  (10 errors). Landed as its own commit.
- **verification:** 6 new store tests (`packages/editor/src/timelineStore.test.ts`) — each one
  confirmed to *fail* against the old shape before being confirmed to pass against the new;
  122/122 frontend tests green; 162/162 Rust tests green including the new torn-write regression,
  which was likewise confirmed to fail (150/600 torn reads) against the old `fs::write`.
- **residual risk, stated honestly:** the dev-mode HMR/page-reload race itself is not eliminated
  and cannot be from inside the app — it is Vite reloading the page under a running IPC bridge.
  What is now true is that it can no longer *strand* the Edit tab: a lost response times out, a
  stale result cannot clobber a good one, the retry ladder recovers on its own, and if it truly
  can't recover the screen says what actually went wrong instead of something false.

## B-033 — Cross-track sync-lock ripple (D-106/D-107) could corrupt a real project: repeated ripple operations kept re-splitting an already-split fragment, producing a chain of ever-smaller slivers and the same clip id duplicated on one track at wildly different positions
status: fixed (2026-09-04, D-109) · severity: blocker (real, confirmed data corruption on the owner's actual saved `New.chroma` project — not a UX surprise, actual timeline structure damage) · area: `packages/editor/src/timeline.ts`, `crates/chroma-timeline/src/lib.rs`
- **found:** owner, live, two reports in quick succession right after D-107 shipped. First: "i moved something in Video 1 and video 2 got shifted" (a same-track `move` triggering an unexpected cross-track shift — sync-lock working as designed, per D-107's own question-1 answer, but foreshadowing the real bug). Second, severe: "i delete this and all of them moves" — closing a gap (D-105's "Close Gap") on a multi-track project. Screenshots showed the total project duration *growing* after closing a gap (`00:26:12:11` → `01:01:08:00` → `00:52:30:18` across two operations) when closing a gap should only ever shrink it, and Video 1/2/3 all displaying the identical source clip stacked at the same position.
- **confirmed on the real file:** `~/Movies/Chroma/New.chroma/project.json` (modified timestamp matching the incident) had genuine corruption in `timelines[0].tracks`: one clip id appearing **3 times within the same track's own clip list** at three unrelated positions, and a second clip id appearing **4 times** as consecutive 166-frame slivers — a track's clip list should never contain the same id twice, let alone three or four times.
- **cause:** D-106/D-107's `rippleShiftWithAutoSplit`/`ripple_shift_with_auto_split` auto-split a clip straddling the ripple point on a sync-locked OTHER track, rather than rejecting — a deliberate design call at the time (matching DaVinci Resolve's real behavior, avoiding sync-lock blocking ripples constantly whenever a straddling clip like a music bed sits on a synced track). What wasn't caught: **repeated** real ripple operations (several genuine `remove_gap`/`move` calls across one editing session — an entirely normal usage pattern, not misuse) each independently correct in isolation could keep re-splitting a fragment a PREVIOUS ripple had already created, since nothing distinguished "an untouched original clip" from "a byproduct of an earlier synthetic split." All 93 pre-existing unit tests (single-operation cases) passed throughout — the bug lived entirely in the cross-operation, cumulative case those tests never exercised.
- **fix:** reverted auto-split back to D-104's own already-proven-safe reject-on-straddle contract, generalized cross-track (`hasStraddlingSyncLockedClip`/`has_straddling_sync_locked_clip`, checked upfront against the pre-mutation tracks at all three ripple call sites — `add_clip` insert, `move`, `remove_gap` — before any clone/mutation happens; new Rust `TimelineError::SyncLockedStraddle`). A straddling clip on a sync-locked track now rejects the whole op outright, same as an unresolvable same-track overlap already did — never splits, so there is no fragment for a later operation to re-split. New regression tests in both languages apply the same rejected op 5x in a row and assert zero fragmentation, zero duplication, proving the cascade is structurally impossible now rather than just less likely. Auto-split may return later as a real, separately-scoped, separately-verified follow-up (a real feature loss, not free — sync-lock now blocks a ripple whenever a straddling clip sits on a synced track, requiring the user to handle it manually) — full writeup: D-109.
- **owner's real project data:** confirmed corrupted on disk, no clean automated recovery exists — the only backup found (`~/Movies/Chroma/_backups/project.json.pre-unify-20260903-131757`) predates an entire day of legitimate editing and restoring it would be a worse loss than the corruption itself; the in-app undo/redo stack almost certainly did not survive, since the dev app was restarted multiple times between the corrupting operations and this fix landing. The corruption pattern is irregular (not a uniform fragmentation chain for every affected clip — some duplicates sit at unrelated positions, not adjacent slivers), so an automated reconstruction script was judged too risky to attempt blind; **recommended path is manually rebuilding the affected clip positions on Video 1-4 through the (now-fixed) UI** — the underlying media files themselves are completely untouched, only the timeline's clip-position bookkeeping was corrupted.

## B-032 — Tauri listener cleanup could throw when Vite HMR reloaded mid-flight, corrupting the IPC bridge — a THIRD distinct root cause behind "No project open"
status: **superseded — this fix did NOT hold; re-fixed in B-034/D-112** (2026-09-04, D-108) · severity: high (dev-mode-only — this specific failure mode cannot occur in a production build — but frequent enough this session to repeatedly masquerade as the project-open bug, across a night where two other genuinely different root causes for the same surface symptom were already found and fixed) · area: `app/src/App.tsx`, `app/src/hooks/useTauriListeners.ts`, `app/src/hooks/useChromaControl.ts`, `app/src/window/TitleBar.tsx`, `app/src/components/modals/{NegativeConversionModal,DenoiseModal}.tsx`
- **found:** owner, live, hit "No project open" again on a freshly restarted app instance — the same surface symptom as **B-004** (historical: entry module double-execution corrupting Tauri IPC on every cold boot) and **B-031** (this session: an `open_manifest` index-space mismatch), but neither of those root causes was in play here — B-004's fix was verified still correctly in place, and B-031's fix (`373e725`) is separately confirmed correct. This is a genuinely third, distinct cause producing the identical symptom.
- **cause:** every `listen()`/`onResized()` call in the app returns `Promise<UnlistenFn>`; the standard React-effect cleanup (`unlistenPromise.then((f) => f())`) races Vite's dev-mode HMR module-reload against that promise resolving. If HMR reloads the module graph — frequent this session, given many concurrent forks editing frontend/backend files against one shared running dev instance — while the promise is still pending, the resolved unlisten function can be invoked against a `window.__TAURI_INTERNALS__` bridge that no longer matches what registered it, throwing `TypeError: Cannot read properties of undefined (reading 'unregisterListener')` inside Tauri's own `_unlisten`. Tauri's own console warning names this exact scenario directly: `Couldn't find callback id N. This might happen when the app is reloaded while Rust is running an asynchronous operation`. Confirmed live: the error fired 2 minutes after a clean boot, well before any project-open attempt; a later idle-window test (150+ seconds, zero concurrent Rust/fork activity) showed zero recurrence, consistent with an HMR-timing trigger rather than a deterministic code defect.
- **fix:** a new shared `safeUnlisten()` helper (`app/src/utils/tauriListeners.ts`) guarding both the promise rejecting and the resolved function itself throwing, replacing six independent, inconsistent hand-rolled cleanup patterns (one of which already had an ad-hoc `.catch()` that only covered half the failure mode). Doesn't eliminate the underlying dev-mode HMR/async-IPC race — makes it silent and harmless instead of an unhandled rejection that can leave the IPC bridge broken for the rest of the session. Full writeup, including the honest verification-gap disclosure (couldn't force-reproduce the race on demand): D-108 in `docs/08-decisions.md`.
- **⚠️ that fix did not actually work — see B-034/D-112.** `try { f?.(); } catch {}` guards only a *synchronous* throw. Tauri's `listen()` resolves to `async () => _unlisten(…)`, and `_unlisten` is itself `async`, so the failure arrives as a **rejected promise** the `catch` cannot see, and the promise was then dropped unhandled. The owner's dev log on a freshly restarted instance built with this fix in it shows the identical error still firing, stack pointing at that exact line. B-034 re-fixed it by chaining the result into the helper's own `.catch`. The verification gap this entry honestly flagged ("couldn't force-reproduce the race on demand") is precisely where it slipped through.
- **process note:** a clean dev-server restart right before testing (rather than trusting HMR through a burst of concurrent edits) avoids this failure class' trigger entirely — worth doing as standard practice whenever several forks have been editing frontend files concurrently, not just after a Rust change.

## B-031 — Opening a project silently aborted before the Edit tab ever saw it, whenever an earlier clip shared a source path with the active one — no error, no log, "No project open" forever
status: fixed (2026-09-04) — **cause #3 of 5 for this symptom; read B-034/D-112 for the pattern across all five and why the screen kept lying about it** · severity: blocker (opening a project is the app's entry point — this recurred across the night, reported fixed twice before the real cause was found) · area: `app/src-tauri/src/chroma/project.rs` (`open_manifest`)
- **found:** owner, live, repeatedly, across the night — same "No project open" / launcher-screen-doesn't-transition symptom kept recurring after two earlier passes (B-025/D-085's loading-spinner-and-retry fix, and this session's own initial project-open regression chase) each addressed a real but different contributing issue without landing the actual root cause. `app.log` showed the backend completing a normal-looking open (grade migration ran, warnings logged) with **zero errors anywhere** — the strongest clue the failure was silent, not crashing.
- **cause:** `open_manifest` resolved the active clip's session index by finding its source path's position in `online_paths`, a `Vec` pushed once per *clip* in manifest order — but the real decode session (`state::Session`) deduplicates by path, so whenever an earlier clip in the manifest shared a source path with the active clip, the two index spaces diverged. `session_set_active` then correctly rejected the now-wrong index, and that rejection aborted the whole open **before `state::set_project` ever ran** — with the error swallowed rather than surfaced to the UI, so the launcher screen just... never transitioned, silently.
- **fix:** resolve the active clip's index against the session's own deduplicated path list instead of the raw per-clip one. 161/161 Rust tests pass, `cargo clippy` clean.
- **process note, disclosed rather than smoothed over:** the fix's own commit message cited "B-030" — already claimed by the unrelated overlap bug directly below, a real numbering collision caught only when the owner asked "do we have this logged as open?" and it turned out not to be logged under any number at all. This B-031 entry is the correction; the fix itself (commit `373e725`) was real and already verified before this doc gap was found.

## B-030 — A clip dragged (same-track or cross-track) could land directly overlapping another clip already there, instead of resolving to a real open/rippled position
status: fixed (2026-09-04, D-104) · severity: high (a core, constant-use interaction — the whole point of D-100's unified clip-move mechanism — producing a silently broken, visually overlapping timeline state) · area: `packages/editor/src/TimelinePane.tsx`, `packages/editor/src/timeline.ts`, `crates/chroma-timeline/src/lib.rs`

  Motion tab, D-046) alongside a component that renders a
  `React.ElementType`-typed prop via JSX (`<Component {...props}>` where

  the program.

  component changed.
- **cause:** `@react-three/fiber` augments the **global** `JSX.IntrinsicElements`
  interface (that's how `<mesh>`, `<group>`, etc. type-check anywhere) — a
  program-wide effect, not scoped to files that import r3f. Once present,
  `React.ElementType` (`keyof JSX.IntrinsicElements | ComponentType<any>`)

  (`Icon` prop).

  `createElement(Icon, { size: 18 })` in place of JSX for that one call in
  each file — behaviorally identical (JSX desugars to the same call at
  runtime; this changes nothing about what renders), but `createElement`'s
  generic signature doesn't distribute over `JSX.IntrinsicElements` the same
  way JSX's own type-checking does, so it type-checks correctly whether or
  not r3f's augmentation is present.
- **verification:** a strict `tsc --noEmit` diff of `app/` before vs. after
  the full Motion tab change (file list, not just count) came back
  byte-identical (64 errors either side) — used specifically to catch every

  component elsewhere in the codebase would show up the same way if r3f's
  augmentation reaches its program later.
